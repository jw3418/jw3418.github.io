# Feature Toggle — 대규모 서비스에서 기능을 제어하는 방법

서비스를 운영하다 보면 코드에 문제가 없어도 특정 기능을 잠시 꺼야 할 때가 있다. 트래픽이 집중되는 동안 부가 기능의 처리를 줄이거나, 운영 정책에 맞춰 기능의 제공 여부를 바꿔야 하는 경우다. 반대로 새 기능을 배포하되 처음부터 모든 사용자에게 공개하고 싶지는 않을 수도 있다.

이런 변경을 매번 코드 수정과 배포로 처리하면, 기능의 운영 시점이 배포 일정에 묶이게 된다.

여기에서 한 가지 질문이 생긴다.

> 같은 버전의 애플리케이션을 유지하면서 기능의 실행 여부만 바꿀 수는 없을까?

Feature Toggle은 이 문제를 해결하는 방식이다. Feature Flag라고도 부르며, 두 용어는 흔히 같은 의미로 사용된다.

처음에는 설정값 하나를 확인하는 조건문으로 보인다. 하지만 여러 서버가 동시에 요청을 처리하는 환경에서는 설정을 어디서 읽는지, 언제 반영되는지, 읽지 못하면 어떻게 동작하는지가 중요해진다.

---

## 배포와 기능 활성화를 분리한다

Feature Toggle의 기본 구조는 단순하다. 코드에 준비된 실행 경로 중 어떤 경로를 사용할지 설정을 보고 결정한다.

다음 예시를 보자. 특정 라이브러리의 API가 아닌 구조를 설명하기 위한 코드다.

```java
public SearchResult search(SearchRequest request) {
    boolean useNewSearch = featureFlags.isEnabled(
        "search-v2",
        request.getUserId(),
        false
    );

    if (useNewSearch) {
        return newSearchService.search(request);
    }

    return existingSearchService.search(request);
}
```

새 검색 기능과 기존 검색 기능이 같은 버전에 포함되어 있다. 실행 시점에 플래그를 평가해 어느 쪽을 사용할지 결정한다. 여기서 `false`는 평가에 실패했을 때 사용할 기본값으로, 기존 검색을 유지한다는 의미다.

이처럼 코드를 서버에 올리는 Deployment와 사용자에게 기능을 제공하는 Release를 분리할 수 있다. 다만 플래그를 켠다고 새로운 로직이 만들어지는 것은 아니다. **선택할 실행 경로가 미리 구현되어 있어야 한다.**

사용 목적에 따라 설계도 달라진다.

| 목적 | 사용 예시 | 설계 시 관심사 |
| --- | --- | --- |
| 새 기능 공개 | 검증 후 점진적으로 활성화 | 공개 대상, 기존 경로로 복귀 |
| 운영 제어 | 부하가 큰 부가 기능 일시 중단 | 차단 범위, 반영 지연 |
| 실험 | 사용자 그룹별로 다른 기능 제공 | 그룹 유지, 결과 측정 |

이러한 용도 구분은 [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html)에서도 다룬다. 이 글에서는 그중 백엔드의 실행 경로를 제어할 때 필요한 구조와 운영상의 판단에 집중한다.

---

## 설정을 관리하는 곳과 판단하는 곳

어드민은 플래그를 변경하는 인터페이스 중 하나다. 설정은 DB나 별도의 설정 서비스에 저장할 수 있고, 애플리케이션은 그 설정을 읽어 실행 여부를 판단한다.

여기서는 두 역할을 나눠볼 필요가 있다.

- **설정 관리:** 누가 어떤 환경의 어떤 기능을 켜고 끌 것인가?
- **플래그 평가:** 지금 들어온 요청에 어떤 실행 경로를 적용할 것인가?

전체 ON/OFF라면 저장된 Boolean 값을 읽는 것으로 충분하다. 특정 사용자나 일정 비율에만 기능을 제공하려면 사용자 식별자 같은 요청 정보도 평가에 사용한다. 이를 Evaluation Context라고 한다. [OpenFeature의 평가 API](https://openfeature.dev/specification/sections/flag-evaluation/)도 플래그 키, 기본값, 평가 컨텍스트를 구분한다.

문제는 이 판단이 요청마다 발생할 수 있다는 점이다.

매번 DB나 원격 설정 서비스를 호출한다면, 기능 실행 전에 네트워크 왕복이 추가된다. 요청량이 늘어날수록 설정 조회량도 함께 증가하며, 설정 서비스의 지연이 실제 API 응답 시간에 영향을 줄 수 있다.

대안은 **설정을 주기적으로 받아 로컬에 보관하고, 요청 시점에는 메모리에서 평가하는 방식**이다.

```mermaid
flowchart TD
    Admin["어드민 / 관리 API"] --> Store["설정 저장소"]
    Store -->|설정 동기화| CacheA["인스턴스 A 로컬 설정"]
    Store -->|설정 동기화| CacheB["인스턴스 B 로컬 설정"]
    RequestA["요청 A"] --> EvalA["플래그 평가"]
    RequestB["요청 B"] --> EvalB["플래그 평가"]
    CacheA --> EvalA
    CacheB --> EvalB
```

실제로 Unleash의 백엔드 SDK는 플래그 설정을 가져와 로컬에서 평가하는 구조를 사용한다. [Unleash SDK 문서](https://docs.getunleash.io/sdks)

이 방식은 요청마다 원격 설정 조회를 기다리지 않아도 된다는 장점이 있다. 대신 설정 변경을 각 인스턴스로 전달하는 문제가 남는다.

---

## OFF를 저장한 시점과 실제로 꺼지는 시점은 다르다

인스턴스 A와 B가 각각 설정을 캐시한다고 해보자. 운영자가 플래그를 OFF로 변경한 뒤 A만 새 설정을 가져왔다면, A는 기존 경로를 사용하고 B는 아직 새 기능을 실행할 수 있다.

DB에 같은 값을 저장한다고 해서 모든 서버가 같은 순간에 그 값을 사용하는 것은 아니다.

| 반영 방식 | 장점 | 고려할 점 |
| --- | --- | --- |
| 요청마다 원격 조회 | 로컬 캐시의 갱신 지연을 줄임 | 조회 지연과 장애에 요청 처리가 영향받음 |
| 주기적 Polling | 구현과 장애 복구 흐름이 비교적 단순 | 다음 조회까지 이전 설정 사용 |
| Push / Streaming | 변경을 빠르게 전달 가능 | 연결 단절과 누락 이후 재동기화 필요 |

원격 조회도 모든 실행의 동시 전환을 보장하지는 않는다. 이미 값을 읽은 요청이나 저장소의 복제 지연은 별도로 고려해야 한다.

반영 방식을 선택하려면 먼저 허용할 수 있는 지연을 정해야 한다. 예를 들어 수십 초의 지연이 허용되는 공개 설정이라면 Polling으로 충분할 수 있다. 반면 장애 대응용 토글이라면 변경 전달뿐 아니라 어느 인스턴스까지 반영되었는지도 확인해야 한다.

설정에 버전을 부여하고 각 인스턴스의 적용 버전과 마지막 동기화 시각을 관측하면, ‘저장은 성공했지만 일부 서버는 이전 설정을 사용 중인 상태’를 구분하는 데 도움이 된다.

Push를 적용했다고 즉시 반영이 보장되는 것도 아니다. 연결이 끊긴 인스턴스가 최신 상태를 다시 받아오는 경로가 필요하다. **설정 전파 속도와 전파 실패의 복구를 함께 설계해야 한다.**

## 설정 서버가 응답하지 않으면 어떻게 할까?

로컬 평가 방식에서는 설정 서버와 통신할 수 없어도 마지막으로 받은 값으로 요청을 처리할 수 있다. 하지만 마지막 값이 항상 안전한 값은 아니다.

장애가 발생한 기능을 OFF로 바꿨는데 해당 변경을 받지 못했다면, 이전 ON 상태를 유지하는 것이 오히려 문제가 된다. 반대로 일시적인 통신 실패 때마다 모든 기능을 OFF로 바꾸면 설정 서버의 장애가 서비스 동작을 크게 바꿀 수 있다.

따라서 아래 상황을 구분해야 한다.

| 상황 | 결정할 정책 |
| --- | --- |
| 기동 후 설정을 한 번도 받지 못함 | 기본값으로 서비스할지, 준비 완료를 기다릴지 |
| 설정을 받은 뒤 동기화 실패 | 마지막 정상값을 얼마 동안 사용할지 |
| 키 누락이나 타입 오류로 평가 실패 | 해당 플래그의 기본값을 무엇으로 둘지 |

앞선 검색 예시에서는 평가 실패 시 기존 검색을 선택했다. 새 검색을 사용하지 못하더라도 검색 자체는 제공할 수 있기 때문이다. 반면 기본 동작이 없는 기능이라면 중단 응답이 필요할 수도 있다.

`false`를 공통 기본값으로 지정하는 것만으로 장애 정책이 완성되지는 않는다. 플래그가 의미하는 동작에 따라 OFF의 영향이 달라지므로, 각 기능의 실패 비용을 기준으로 정해야 한다.

## 사용자 10%에게 공개한다는 것은 무엇일까?

점진적 공개에서는 단순 ON/OFF를 넘어 ‘누구에게 켤 것인가’를 결정한다.

요청마다 난수를 생성해 10% 확률로 새 기능을 선택하면, 같은 사용자도 요청할 때마다 다른 기능을 사용할 수 있다. 사용자 그룹을 유지하려면 안정적인 식별자를 기준으로 대상을 나눠야 한다.

개념적으로는 다음과 같이 표현할 수 있다.

```text
bucket = stableHash(flagKey, userId) % 10000
새 기능 사용 = bucket < 1000
```

여기서 해시는 음수가 아닌 버킷 값을 만들도록 정규화했다고 가정한다. 같은 입력은 같은 버킷에 배정되므로, 해시 규칙과 키를 유지한 채 기준을 1000에서 2000으로 늘리면 기존 공개 대상을 포함하면서 범위를 확대할 수 있다. 이런 성질을 Stickiness라고 부른다. [Unleash의 Stickiness 설명](https://docs.getunleash.io/concepts/stickiness)

대규모 서비스에서는 식별자 선택도 중요하다. 사용자 단위인지, 세션 단위인지, 조직 단위인지에 따라 경험이 달라진다. 여러 서비스가 같은 대상을 판단해야 한다면 식별자와 해시 알고리즘, 설정 버전도 맞아야 한다.

또한 사용자 10%와 요청량 10%는 다르다. 선택된 사용자 중 호출량이 많은 사용자가 포함되면 실제 부하는 더 커질 수 있다. 공개 비율을 늘릴 때는 비율 자체보다 오류율, 지연 시간, 하위 시스템 부하를 함께 확인해야 한다.

## 하나의 요청에서는 어떤 결정을 유지할까?

같은 요청 안에서도 설정이 바뀔 수 있다. 처리 초반에는 ON을 읽고, 저장 직전에는 OFF를 읽는다면 앞뒤 로직이 서로 다른 경로를 전제로 실행될 수 있다.

한 작업이 동일한 동작을 유지해야 한다면 시작 시점의 평가 결과를 보관해 후속 처리에 전달하는 방식을 고려할 수 있다. 여러 서비스에 걸친 흐름이라면 신뢰할 수 있는 내부 컨텍스트에 선택된 실행 경로를 담는 방법도 있다.

다만 이 방식에서는 처리 도중 OFF로 바꿔도 이미 시작된 작업은 기존 결정을 유지한다. 신규 요청을 막는 것과 진행 중인 작업까지 중단하는 것은 요구가 다르다.

특정 시점 이후 쓰기를 반드시 막아야 한다면 토글 검사만으로 충분하지 않을 수 있다. 검사 직후 설정이 바뀌는 경쟁이 남기 때문에 작업 종료 절차나 쓰기 경계의 동시성 제어가 추가로 필요하다.

적용 경로도 확인해야 한다. 화면을 숨겨도 API 직접 호출이나 배치 실행이 남아 있을 수 있으므로, 실제 작업을 수행하는 백엔드에서 정책을 적용해야 한다. Feature Flag는 인증·인가를 대체하지 않으며, 클라이언트가 전달한 플래그 값만으로 실행 권한을 결정해서도 안 된다.

기능을 OFF로 되돌리는 경우에는 데이터 호환성도 남는다. 새 경로가 기록한 데이터를 기존 경로가 읽을 수 없다면 플래그만 되돌려서는 정상 동작하지 않는다. **기능 비활성화는 데이터 변경까지 되돌려주지 않는다.**

## 토글도 운영 대상이 된다

Feature Toggle을 도입하면 같은 코드 버전에서도 설정에 따라 실행 결과가 달라진다. 장애가 발생했을 때 배포 이력만 확인해서는 원인을 찾기 어려워진다.

변경 이력에는 환경, 변경자, 변경 시각, 이전 값과 새 값을 남겨야 한다. 실행 측면에서는 플래그별 평가 결과, 기본값 사용 여부, 설정 동기화 실패를 관측할 수 있어야 한다. 모든 평가를 로그로 남기면 요청량에 비례해 비용이 커지므로 집계 지표와 필요한 범위의 샘플링을 구분하는 편이 낫다.

검증 대상도 ON 상태만으로 끝나지 않는다. 기존 경로, 평가 실패, 설정 전파 지연, 다시 OFF로 전환하는 상황을 확인해야 한다. 특히 Rollout 중에는 코드 버전과 설정 버전이 섞일 수 있으므로 새 설정을 이전 코드가 받아도 안전한지 살펴볼 필요가 있다.

토글을 제거할 시점도 정해야 한다. 새 기능 공개가 끝난 뒤에도 기존 분기를 계속 남겨두면 읽어야 할 코드와 테스트 범위가 늘어난다. 서로 독립적인 Boolean 플래그가 n개라면 가능한 조합은 최대 2ⁿ개다. 모든 조합을 동일하게 검증하기보다 실제 운영 조합과 상호작용이 있는 경계를 우선하되, 불필요한 플래그 자체를 줄이는 것이 먼저다.

공개 완료 후 제거할 토글과 장기적으로 유지할 운영 토글을 구분하고, 소유자와 제거 조건을 기록해두면 방치된 분기를 줄일 수 있다. 오래 유지하는 비상 토글도 OFF 경로가 계속 동작하는지 확인해야 한다.

## 어디까지 구현해야 할까?

전체 ON/OFF 몇 개만 필요하다면 DB 설정과 공통 조회 모듈에서 시작할 수 있다. 요청량 때문에 조회 비용이 문제가 되면 캐시를 추가하고, 사용자별 공개나 여러 서비스의 공통 정책 관리가 필요해졌을 때 평가와 전파 구조를 확장할 수 있다.

처음부터 전용 플랫폼을 도입할 필요는 없다. 다만 대상 조건, 변경 권한, 감사 이력, SDK, 설정 전파까지 직접 구현해야 한다면 관리형 서비스나 기존 도구를 사용하는 비용과 비교할 시점이 된다.

이때 선택 기준은 단순한 트래픽 규모보다 구체적인 운영 요구다. 설정 변경을 얼마 안에 반영해야 하는지, 오래된 값으로 어디까지 처리해도 되는지, 잘못 켰을 때 어떤 경로로 복귀할 수 있는지가 먼저 정해져야 한다.

Feature Toggle은 코드의 실행 여부를 운영 중에 선택할 수 있게 한다. 대규모 서비스에서는 그 선택을 여러 서버가 나눠 수행한다. 따라서 조건문을 추가한 뒤에는 **서버들이 언제 같은 결정을 내리게 되고, 그 전까지 어떤 차이를 허용할 것인지**를 설명할 수 있어야 한다.
